# OmaSeal: publishable omaseal-bin AUR package and release-bump automation

## Goal Capsule

- **Objective:** The `omaseal-bin` package is publish-ready such that, once the maintainer pushes it to AUR, `yay -S omaseal-bin` installs a working, correctly-depended package on x86_64 or aarch64; every release afterwards updates the packaging files with one command instead of hand-editing five paths.
- **Means:** Correct and complete the existing `packaging/aur/` PKGBUILD pair, generate `.SRCINFO`, add a post-release bump script wired into `release.yml`, and document the maintainer publish flow (KTD1, KTD3).
- **Authority:** this plan; the repository's own conventions; AUR packaging standards as evidenced by the existing files.
- **Stop conditions:** the actual AUR submission (needs the maintainer's AUR account and SSH key — user step); any change to upstream `omacom/omarchy-mac` work (separate repo, PR #448 pending).
- **Execution profile:** packaging/config work — proof is build and lint smoke, not unit coverage.
- **Who finishes:** ce-work implements U1–U3; the maintainer performs the one-time AUR account setup and first push described in U3's doc.

## Product Contract

### Summary

`packaging/aur/` already contains a source-build `PKGBUILD`, a `PKGBUILD-bin`, and `.install` hooks with pinned v0.2.2 checksums — but the pair is not publishable: dependencies declare a library the binary never links and hard-require an optional fingerprint daemon, no `.SRCINFO` exists, and every release requires hand-editing five paths (two PKGBUILDs, `install.sh`'s pinned version+checksums, and both regenerated `.SRCINFO` files). This plan makes the `-bin` package correct, adds a one-command bump for all five, wires it into the release workflow as a PR, and documents the AUR maintainer flow. Roadmap v0.6.0 item: "AUR package (`omaseal-bin`) and release automation hardened."

### Problem Frame

The package metadata overstates runtime requirements (`libsecret` is not linked — the binary is pure-Go D-Bus; `ldd` shows libc/libresolv only) and understates optional ones (`wl-clipboard` for clipclear, `pinentry` for GUI prompt, `fprintd` for the biometric agent gate). Without `.SRCINFO` the package cannot be pushed to AUR at all. And the version/checksum pins scattered across `PKGBUILD`, `PKGBUILD-bin`, `install.sh`, and `.SRCINFO` will silently drift on the next release — exactly the class of drift `install.sh`'s embedded checksums were designed to prevent.

### Requirements

- R1. `packaging/aur/PKGBUILD-bin` declares `depends=('org.freedesktop.secrets')`, moves `fprintd`, `wl-clipboard`, and `pinentry` to `optdepends`, and declares `provides=('omaseal')` / `conflicts=('omaseal')`.
- R2. `packaging/aur/PKGBUILD` (source build) receives the same dependency corrections and `conflicts=('omaseal-bin')`; its build-time `makedepends=('go')` stays.
- R3. A `.SRCINFO` exists beside each PKGBUILD, generated by `makepkg --printsrcinfo` — never hand-written.
- R4. One command bumps `pkgver` and per-arch `sha256sums` in both PKGBUILDs, every pinned `v<tag>` literal in `install.sh` — the `OMASEAL_VERSION` default, the `!= "vX.Y.Z"` embedded-checksum guard, and both `EXPECTED_SHA256` values — and regenerates both `.SRCINFO` files for a published tag.
- R5. The bump runs in CI on each release (an `archlinux:latest` container job, since `makepkg` does not exist on Ubuntu runners) and lands as a pull request — not a direct commit to main.
- R6. `docs/packaging.md` documents the one-time AUR maintainer setup and the per-release publish flow for `omaseal-bin`, and names the AUR git push as the maintainer's step.
- R7. `omaseal-bin` builds cleanly under `makepkg` on aarch64 and the resulting package lists `/usr/bin/omaseal`, the shell-plugin files, and the license.

### Success Criteria

- `makepkg --printsrcinfo` output for each PKGBUILD is byte-identical to the committed `.SRCINFO`.
- `pacman -Qip` on the built `omaseal-bin` package shows `org.freedesktop.secrets` as the only hard dependency.
- Running the bump script against the already-published v0.2.2 release reproduces the currently pinned checksums (self-check that proves the script before a new release exists).

### Scope Boundaries

#### Deferred to Follow-Up Work

- Publishing the source-build `omaseal` package to AUR (roadmap names `omaseal-bin`; the source PKGBUILD stays maintained for completeness).
- CI-driven AUR push gated on an `AUR_SSH_PRIVATE_KEY` repository secret — docs describe the manual push; automation can follow once the maintainer elects it.
- An `omaseal-git` package building from HEAD.

#### Outside this product's identity

- The actual AUR account creation, package registration, and `git push` to `aur.archlinux.org` — a maintainer action with external side effects.
- Coexistence policy between the packaged `io.github.duketopceo.omaseal` plugin and upstream's `shell/plugins/secrets` (PR #448) — different plugin IDs, both can be installed; flag if upstream review raises it.
- Merging the open OmaSeal PR stack (#6, #8) — the package pins released tarballs, so the next release needs those landed first, but the merges are their own decision.

## Planning Contract

### Key Technical Decisions

- KTD1. **Publish `omaseal-bin` as the first AUR package.** (session-settled: user-approved — chosen over leading with the source-build `omaseal` package: the roadmap entry the user directed names `omaseal-bin`, and repackaging CI-built tarballs reuses the same checksum trust model `install.sh` already ships.) The source `PKGBUILD` is corrected in lockstep so it does not rot.
- KTD2. **`depends` uses the `org.freedesktop.secrets` virtual provide; optional integrations move to `optdepends`.** The binary is pure Go on D-Bus — `libsecret` is never linked (`ldd` on the installed binary shows libc/libresolv only). `gnome-keyring` satisfies the virtual provide on Omarchy, and the name lets other Secret Service providers satisfy it elsewhere.
- KTD3. **Release bump is a script plus a CI-opened PR, not an auto-commit and not a CI AUR push.** The checksums can only be computed after release artifacts exist, so the bump is inherently post-release; a PR keeps the repo's PR-first norm and lets the maintainer eyeball the pinned hashes. AUR's `git push` needs the maintainer's SSH key, which the agent must not provision.
- KTD4. **The package also installs the shell plugin under `/usr/share/omarchy/shell/plugins/io.github.duketopceo.omaseal`.** Existing behavior in both PKGBUILDs is kept: the omaseal-aware panel is a distinct feature from upstream's generic `secrets` panel and they coexist under different plugin IDs.

### Assumptions

- The maintainer (user) performs AUR account creation, SSH key upload, and the first `git push` to `aur.archlinux.org` — recorded because no synchronous user was present to confirm.
- `aarch64` `makepkg` build on the dev host is accepted as the build-proof for the `-bin` recipe shape; `x86_64` gets the same code path with a different `source_` array and checksum, and its artifact correctness rests on CI having produced the tarball.
- `.SRCINFO` files are committed in-repo next to the PKGBUILDs so the publish step is a plain copy into the AUR clone; regenerating them in CI (KTD3's PR) keeps them fresh.

## Implementation Units

### U1. Correct dependency declarations and generate `.SRCINFO`

**Goal:** Both PKGBUILDs describe real runtime needs and carry the metadata AUR requires.

**Requirements:** R1, R2, R3, R7

**Files:** `packaging/aur/PKGBUILD`, `packaging/aur/PKGBUILD-bin`, `packaging/aur/.SRCINFO` (new — generated from the source PKGBUILD), `packaging/aur/omaseal-bin.SRCINFO` (new — generated from `PKGBUILD-bin`; kept under that name so the two never collide, and U3's publish step copies it into the AUR clone as `.SRCINFO`)

**Approach:**

1. In `PKGBUILD-bin`: replace `depends=('gnome-keyring' 'libsecret' 'fprintd')` with `depends=('org.freedesktop.secrets')`; add `optdepends` for `fprintd` (biometric agent unlock), `wl-clipboard` (clipclear and panel copy), and `pinentry` (GUI unlock prompt) with the standard `optdepends=('name: description')` form; add `provides=('omaseal')` and `conflicts=('omaseal')`.
2. In `PKGBUILD`: same dependency split, plus `conflicts=('omaseal-bin')`; `makedepends=('go')` stays.
3. Generate `.SRCINFO` per package via `makepkg --printsrcinfo` (run with the PKGBUILD under the name `PKGBUILD` in a scratch dir, since `--printsrcinfo` keys off the literal filename).
4. Leave `pkgver`/`pkgrel`/checksums untouched — U2 owns the bump story.

**Execution note:** This is mostly packaging/config; prefer build/lint smoke verification over unit coverage.

**Test scenarios:**

- `makepkg --printsrcinfo` on `PKGBUILD-bin` emits `depends = org.freedesktop.secrets` and no `libsecret`/`fprintd` hard deps.
- `makepkg --printsrcinfo` on `PKGBUILD` shows `makedepends = go` and `conflicts = omaseal-bin`.
- The committed `.SRCINFO` files are byte-identical to fresh `--printsrcinfo` output (no hand edits).
- `bash -n` passes on both `.install` files (unchanged, but re-verified in the same pass).

**Verification:** `--printsrcinfo` runs without error on both; namcap on the built package (see Verification Contract) reports no missing-dependency warnings. namcap's "dependency included and not needed" warning for `org.freedesktop.secrets` is an expected false positive — namcap derives deps from `ldd`, and a pure-Go binary's D-Bus runtime dep has no link-level footprint; do not drop the dep to silence it.

### U2. Post-release bump script and CI job

**Goal:** One command refreshes every pinned version/checksum for a published tag; CI opens a PR with the result so it is never forgotten or hand-edited wrong.

**Requirements:** R4, R5

**Dependencies:** U1 (the files it rewrites must be correct first)

**Files:** `packaging/aur/bump.sh` (new), `Makefile` (optional `release-bump` target delegating to the script), `.github/workflows/release.yml`, `install.sh`

**Approach:**

1. `packaging/aur/bump.sh <tag>` downloads `sha256sums.txt` (and `sha256sums.txt.asc` when present) from the published GitHub release. All downloaded release content is untrusted input — parse fields with `grep`/`awk` only, never `source`/`eval` it or expand its contents unquoted. When the `.asc` exists, verify it against the pinned `OMASEAL_SIGNING_FINGERPRINT` mechanism `install.sh` already ships; when the release is unsigned, require an explicit `--allow-unsigned` flag so single-channel checksum trust is a deliberate act, not a silent default. The script then rewrites `pkgver` (and resets `pkgrel=1`) and both per-arch `sha256sums_*` arrays in `PKGBUILD-bin`, rewrites `pkgver` and `sha256sums` in `PKGBUILD` (the source-tarball hash needs the tag's archive tarball checksum — fetch `…/archive/refs/tags/v${ver}.tar.gz` and hash it), rewrites **every** `v<old-tag>` literal in `install.sh` — the `OMASEAL_VERSION` default (line ~41) *and* the `!= "vX.Y.Z"` embedded-checksum guard (line ~68), which blanks `EXPECTED_SHA256` on a mismatch and would silently disable embedded verification after the first real bump — plus both `EXPECTED_SHA256` values, then regenerates both `.SRCINFO` files.
2. The script fails loudly (nonzero, named missing piece) when the tag's release or sums file is absent — it must never write placeholder or `SKIP` sums. A post-run self-assertion greps `install.sh` for any remaining `v<old-tag>` literal and confirms `EXPECTED_SHA256` is non-empty, so a missed pin site fails the run rather than shipping a weaker installer.
3. `release.yml` gains a `bump-packaging` job running after `release`, inside `container: archlinux:latest` (job permissions: `contents: write`, `pull-requests: write`; `GH_TOKEN` from `secrets.GITHUB_TOKEN`). The container setup must account for three facts: GitHub container jobs run as root and `makepkg` refuses root even for `--printsrcinfo`, so create a non-root `builder` user and run the makepkg invocations via `runuser -u builder`/`su builder -c` in a builder-owned scratch dir; `gh` is not in the archlinux image nor injected into container jobs, so the pacman line is `pacman -Sy --noconfirm base-devel git github-cli`; and the repo's `persist-credentials: false` checkout leaves git with no push credentials on a detached tag HEAD, so the job creates a named `bump/<tag>` branch, sets git `user.name`/`user.email`, and runs `gh auth setup-git` before `gh pr create`. Pre-flight: the repo's Actions setting "Allow GitHub Actions to create and approve pull requests" must be enabled, and GITHUB_TOKEN-authored PRs do not trigger `ci.yml`'s `pull_request` checks — the bump PR merges on maintainer review. A self-check step asserts the diff touches only the five intended paths.
4. Keep the script Arch-host-runnable too — it is the same command a maintainer runs locally, which is what makes CI's use of it trustworthy.

**Technical design:** The self-check against v0.2.2 doubles as the script's acceptance test: run `bump.sh v0.2.2` in a scratch checkout and require a no-op diff on checksums (pkgver may differ only if the tag format changed).

**Test scenarios:**

- `bump.sh v0.2.2` against the live release reproduces the checksums already pinned in `PKGBUILD-bin` and `install.sh` (no-op where pins already match).
- `bump.sh v9.9.9` (nonexistent tag) exits nonzero and writes nothing.
- The generated `.SRCINFO` files match `makepkg --printsrcinfo` output for the bumped PKGBUILDs.
- The workflow job's diff scope is asserted to `packaging/aur/*`, `install.sh` — anything wider fails the job.

**Verification:** `bash -n` on the script; a real run against v0.2.2 produces the expected no-op result; the workflow file passes YAML lint and the new job's `gh` invocation is exercised at least by `--dry-run`-equivalent review (no real release exists to test the job end-to-end — record that as the residual).

### U3. Maintainer publish documentation

**Goal:** `docs/packaging.md` lets the maintainer publish and maintain `omaseal-bin` without re-deriving the AUR mechanics.

**Requirements:** R6

**Dependencies:** U1 (documents the final file set), U2 (documents the bump flow)

**Files:** `docs/packaging.md` (new), `README.md` (install section's existing AUR lines corrected), `SUBMISSION.md` (same correction + removal path)

**Approach:**

1. One-time setup: AUR account, SSH key upload, `git clone ssh://aur@aur.archlinux.org/omaseal-bin.git`, copy `PKGBUILD-bin` as `PKGBUILD`, `omaseal-bin.SRCINFO` as `.SRCINFO`, and `omaseal-bin.install` under its own name (the `install=` key in the PKGBUILD references it), commit, push.
2. Per-release flow: merge the CI bump PR, copy the three files into the AUR clone, push; note that `updpkgsums`-style bumps must never publish `SKIP` sums (both PKGBUILDs already carry that comment — the doc names it a hard rule).
3. Local verification recipe: `makepkg -f` build, `pacman -Qip`, `namcap` when installed; state plainly that `makepkg -si`/`pacman -U` need sudo.
4. Three honest notes: the AUR package installs `/usr/bin/omaseal` (which can shadow `~/.local/bin/omaseal` from `install.sh` — PATH order decides); the packaged plugin `io.github.duketopceo.omaseal` installs to Omarchy's first-party dir, which the shell prefers over a same-ID copy in `~/.config/omarchy/plugins` — installing the package silently switches which copy runs, and removing it resurrects the stale user copy; and removal is `pacman -R omaseal-bin`, not the `rm ~/.local/bin/omaseal` path documented for `install.sh` installs.
5. README and SUBMISSION.md already list `yay -S omaseal` for the source package — which this plan does not publish. Correct the existing AUR lines rather than adding new ones: lead with `yay -S omaseal-bin`, and remove the `yay -S omaseal` line (or mark it "planned, not yet published") in both files until the source package ships. Also update SUBMISSION.md's removal instructions to cover `pacman -R omaseal-bin`.

**Test scenarios:**

- Every command in the doc is copy-pasteable and names real files that exist after U1/U2 (checked by re-reading the doc against the tree).
- The doc states the AUR push is the maintainer's step — no instruction implies the agent or CI does it.

**Verification:** Doc reviewed against the final `packaging/aur/` contents; README renders (no broken links — run a link check on the new anchors).

### Residuals and maintainer decisions (document review, 2026-09-15)

- The CI bump job's `gh pr create` path is unexercised until the next real tag — stated in the PR body. Pre-flight before relying on it: the repo's Actions setting "Allow GitHub Actions to create and approve pull requests" must be enabled, and GITHUB_TOKEN-authored bump PRs do not trigger `ci.yml`'s `pull_request` checks, so they merge on maintainer review.
- Whether GPG signing (`GPG_KEY_ID`/`GPG_PRIVATE_KEY` release secrets) becomes mandatory before AUR publication is a maintainer decision. - `omaseal doctor` hard-checks `gnome-keyring-daemon` by name (`engine/doctor.go`); under non-GNOME Secret Service providers (keepassxc, oo7) the package works over D-Bus but doctor misreports the service as missing. Follow-up, out of packaging scope.

- README's embedded `v0.2.2` examples sit outside the bump diff scope — accepted cosmetic drift, revisited if it confuses anyone.
